### Q1: Did GoReleaser ever build the "pipe on goreleaser"? — ANSWER: NO, still not built, confirmed open as of 2025-03-11

**VERIFIED (primary source):** github.com/goreleaser/goreleaser issue #4565 "Integrating godownloader into goreleaser" — https://github.com/goreleaser/goreleaser/issues/4565
- Filed 2024-01-22 by a user requesting exactly this: "goreleaser creates shell scripts like godownloader and publishes them."
- caarlos0 (GoReleaser author/maintainer) replied 2024-01-29: *"this is something I've been wanting to do for a while (since godownloader was created, actually). but yeah, I need to do it eventually... good to have an issue for it as well"*
- kishaningithub offered community help 2024-08-24, no response recorded in thread.
- andreynering (go-task maintainer) commented 2025-03-11: *"We still rely heavily on godownloader for Task, despite being deprecated. Having this integrated officially would be awesome."*
- **STATE: issue is OPEN, unresolved, as of the last comment (2025-03-11).** No native GoReleaser install-script generation/pipe exists as of this survey (2026-07-16). This is a *direct, dated confirmation* that the gap caarlos0 identified in 2019 is STILL a gap 6+ years later — GoReleaser itself never solved it.

**VERIFIED:** GoReleaser's own current install docs (https://goreleaser.com/getting-started/install/oss/, fetched 2026-07-16) list: Homebrew tap, npm, snapcraft, scoop, chocolatey, winget, apt, yum, AUR, nixpkgs, `go install`, Docker, manual binary download, and a bash script `curl -sfL https://goreleaser.com/static/run | bash`. That script is GoReleaser's own install-of-GoReleaser mechanism (uses `goreleaser/godownloader`-style hosted script at `goreleaser.com/static/run`), NOT a generator/template offered to GoReleaser *users* for distributing *their own* tools. No mention found of `install.goreleaser.com`, curl|sh guidance for consumers' own projects, or any documented recommendation for how GoReleaser users should ship install scripts for binaries built with GoReleaser.

**VERIFIED:** `install.goreleaser.com` (the old hosted godownloader-tree service, pattern `install.goreleaser.com/github.com/<owner>/<repo>.sh`, where projects were added via PR adding a YAML file to a "godownloader tree" folder) **no longer resolves in DNS** (`getent hosts install.goreleaser.com` → NXDOMAIN, checked 2026-07-16, while `goreleaser.com` and `github.com` resolve fine from the same host — ruling out a general network/sandbox issue). Wayback Machine's `archive.org/wayback/available` API returns **zero archived snapshots** for both `install.goreleaser.com` and the goreleaser.sh sub-path (checked 2026-07-16) — could not independently confirm via Wayback what the service used to output, only that it's gone now. Google's index still shows stale cached titles ("Install | GoReleaser") for the dead domain.
- Consistent with godownloader repo being archived 2022-01-14 (`gh repo view goreleaser/godownloader`: `isArchived: true`, `archivedAt: 2022-01-14T01:58:29Z`, `pushedAt: 2021-07-17` — last code push mid-2021).

**Conclusion so far for Q1:** The "pipe on goreleaser" caarlos0 floated in 2019 was never built. It remains an open, acknowledged-but-unstaffed feature request as of March 2025. GoReleaser today gives its users NO native tooling for install-script generation.

### Q2: godownloader's descendants — go-task still on it, golangci-lint detached-but-kept-the-code

**VERIFIED:** go-task (`andreynering`, maintainer) states directly in the still-open issue thread (2025-03-11): *"We still rely heavily on godownloader for Task, despite being deprecated."* — i.e., go-task's install.sh is still the (unmaintained, frozen-since-2021) godownloader-generated artifact, not replaced or hand-forked onto something new. Source: https://github.com/goreleaser/goreleaser/issues/4565#issuecomment-2714131179

**VERIFIED:** golangci-lint's `install.sh` (https://github.com/golangci/golangci-lint/blob/master/install.sh, checked 2026-07-16) is a godownloader-generated script built on `client9/shlib` (https://github.com/client9/shlib) — file still contains the verbatim banner "functions from https://github.com/client9/shlib — portable posix shell functions" (lines ~141-389) and its license notice, unmodified in substance. PR golangci/golangci-lint#4407 (merged 2024-02-21, https://github.com/golangci/golangci-lint/pull/4407) only removed the *textual reference* to godownloader in the usage message, with the stated rationale: *"The godownloader project is now archived, so install.sh now live[s] its life independently here."* i.e. **they didn't replace it with a different tool — they just stopped depending on the (dead) generator and now hand-maintain the generated output in place.** Confirmed via godownloader issue #207 (https://github.com/goreleaser/godownloader/issues/207): maintainer caarlos0 declared the whole repo "officially deprecated" — "it hasn't been updated since forever" / "call for maintainers was no good."

**Conclusion for Q2:** The ecosystem did NOT migrate to a new generator after 2022. The two flagship godownloader-descended projects checked (go-task, golangci-lint) both just kept running the frozen 2021-era generated script — one unchanged (go-task), one hand-detached from its origin but structurally identical (golangci-lint). No replacement tool absorbed this niche. This directly undercuts any assumption that "the ecosystem moved on to X" — it mostly didn't move at all.

**shlib licensing note (relevant to option (c) fork/vendor):** client9/shlib (https://github.com/client9/shlib) is the underlying library godownloader/golangci-lint/go-task scripts are built from. Could not fully confirm exact SPDX license id from search snippets alone (LICENSE.md exists in repo, permissive per the "acknowledgement/PRs appreciated, optionally credit via license.sh" convention referenced) — if this path is pursued, read LICENSE.md directly before vendoring.

### dist (formerly cargo-dist, axodotdev) — actively maintained, NOT a shutdown company (contradicts task's premise)

**VERIFIED — premise correction:** The task brief said "axodotdev reportedly wound down — confirm." **Could not confirm; evidence points the other way.** As of check on 2026-07-16:
- `gh repo view axodotdev/cargo-dist`: `isArchived: false`, `pushedAt: 2026-07-07T10:06:27Z` (9 days before this survey), license Apache-2.0.
- Latest release v0.32.0 dated 2026-05-21 (https://github.com/axodotdev/cargo-dist/releases), prior v0.31.0 on 2026-02-23 — regular cadence continuing into 2026.
- axo.dev (the company marketing site) resolves and WebFetch confirms it's a live business site, not a parking page, with client logos (Oxide, Turso, Astral, Ferrous Systems) and active CTAs — despite a stray search-engine snippet suggesting "this website is for sale" (likely stale/misleading cache, not corroborated on direct fetch).
- Caveat: `blog.axo.dev` and `opensource.axo.dev` subdomains returned DNS NXDOMAIN on direct fetch (2026-07-16) even though `axo.dev` itself resolves and Google's index still shows content under those paths — **could not fully explain this discrepancy** (possible subdomain consolidation onto `axodotdev.github.io` for docs, which IS live and current). Docs now primarily live at https://axodotdev.github.io/cargo-dist/book/ (confirmed live, current TOC fetched).
- **Bottom line: dist/cargo-dist is an actively maintained, well-resourced project as of mid-2026, not an abandoned/wound-down one.** Do not treat it as defunct.

**Language support — VERIFIED it is NOT Rust-only, but Go is untested/unconfirmed:**
- Blog post "cargo-dist for any language" (2023-12, referenced via search + archive mirror https://axo-blog.pages.dev/2023/12/generic-builds since blog.axo.dev itself didn't resolve): dist supports "any kind of project, in any kind of language, with any sort of buildsystem" via **generic/custom builds** — you write a `dist.toml` with `binaries` (list of binary names to install) and `build-command` (arbitrary shell command dist runs to produce them), and dist handles archiving/checksumming/installer-generation from there.
- Book has a dedicated "Quickstart → Everyone Else" page (https://axodotdev.github.io/cargo-dist/book/quickstart/everyone-else.html, fetched 2026-07-16): *"dist's generic build support lets you access all the same building and distribution features you get from Cargo-based builds in any language."* Examples cited in blog: C, Objective-C, JS. **No explicit Go example found in official docs** — plausible it works (it just shells out to your build-command and packages whatever binary comes out) but **UNVERIFIED for Go specifically**; would need a spike to confirm.
- Setup still requires installing the Rust-based `dist` CLI itself (via cargo/npm/etc.) as a **release-time** tooling dependency even for non-Rust projects — a new toolchain to add to CI, not just "point it at your goreleaser output."

**No third-party service required at INSTALL time — VERIFIED, this is a real strength:**
- Generated shell installer fetches artifacts from **the consumer's own GitHub Release** ("fetches the best possible archive from your Artifact URL" — https://axodotdev.github.io/cargo-dist/book/installers/shell.html, fetched 2026-07-16), not from any axo-hosted proxy. This is structurally the same trust model release-ci wants (self-hosted, no third-party dependency at curl-time).
- Recommended install command uses GitHub's own `/releases/latest/download/<name>-installer.sh` alias (https://axodotdev.github.io/cargo-dist/book/install.html): `curl --proto '=https' --tlsv1.2 -LsSf https://github.com/OWNER/REPO/releases/latest/download/NAME-installer.sh | sh`. **Architectural mismatch vs. our target**: the installer script itself is a **versioned release artifact re-generated and re-uploaded on every release**, not a single stable script living at a fixed repo path (like our wanted `raw.githubusercontent.com/.../main/install.sh`). GitHub's `/releases/latest/` redirect substitutes for "always current," but there is no single vendored file a consumer repo owns/edits directly — the file is dist-tool output, regenerated by `dist init`/CI each release.
- Found (but not fully chased down) `public.axodotdev.host` — an axo-run mirror/dashboard for releases (e.g. `public.axodotdev.host/releases/github/axodotdev/cargo-dist/...`). Appears to be an **optional** analytics/hosting extra, not a hard dependency for the base shell-installer flow described above — but **not fully verified** whether any default-generated installer silently calls out to it.

**Checksum verification — VERIFIED, automatic since v0.26.0:** Per release notes/changelog summary (v0.26.0, 2024-12-12, https://github.com/axodotdev/cargo-dist/releases/tag/v0.26.0): dist "now embeds checksum information into the shell installer and validates the tarball before unpacking it" — before that release, checksum validation existed only for the Homebrew installer path. Also ships a unified `sha256.sum`-style file. Separately, recent dist releases carry GitHub Artifact Attestations, verifiable via `gh attestation verify <file> --repo axodotdev/cargo-dist` — conceptually parallel to release-ci's cosign/SLSA approach but GH-native rather than cosign/Fulcio.

**Presence-check / --force / --version — NOT CONFIRMED SUPPORTED (documented gaps found):**
- Checked https://axodotdev.github.io/cargo-dist/book/installers/usage.html (fetched 2026-07-16). Documented installer knobs: `<APPNAME>_INSTALL_DIR` (alias `CARGO_DIST_FORCE_INSTALL_DIR`) for custom install dir; `INSTALLER_NO_MODIFY_PATH`; `<APPNAME>_PRINT_QUIET` / `--quiet`; `<APPNAME>_PRINT_VERBOSE` / `--verbose` (since 0.30.0); `<APPNAME>_UNMANAGED_INSTALL` (since 0.23.0).
- **No documented flag for**: idempotent presence-check (exit 0 if already installed at that version), a `--force`/reinstall flag, or a `--version vX.Y.Z` runtime selector on the installer itself. Version selection instead happens by installing from a *specific release's* installer URL (`/releases/download/vX.Y.Z/...` instead of `/releases/latest/...`), which is a different UX than release-ci's wanted `install.sh --version vX.Y.Z` on a single stable script.
- This is a genuine, confirmed gap versus release-ci's requirements list.

**dist verdict:** Real, active, well-engineered, closest philosophical match of anything found so far (self-hosted trust model, auto checksum verification, generic-language support) — but (a) Go support is unverified/undocumented in practice, (b) its installer is a per-release generated artifact rather than a single vendored stable-path script, (c) it lacks native presence-check/--force/--version-flag semantics release-ci explicitly wants, and (d) adopting it means taking on a whole Rust-toolchain-based release tool alongside GoReleaser, not just borrowing a script. Worth reading its generated shell installer source as a **model to imitate** (see if we can fetch an actual example .sh from a real release) rather than adopting the tool wholesale.

### Remaining candidates — generic binary fetchers, declarative managers, hosted services

**Key framing established across all of these:** eget, ubi, binenv, aqua, cargo-binstall are all **tools your USERS install once, then use to fetch many different projects' binaries** ("I have eget, now `eget owner/repo`") — they are NOT scripts a maintainer vendors into their own repo for a bare `curl | sh`. This is a fundamentally different distribution model than release-ci's stated goal (one canonical `install.sh` living at each consumer repo's own root, invoked bare). None of them, by themselves, produce "the file you vendor into gostow/hud/dstow." They're candidates for a *"also mention in your README as an alternative for power users"* footnote at best, not the covered use case.

**eget** (zyedidia/eget, https://github.com/zyedidia/eget) — MIT license. **VERIFIED going stale**: `pushedAt: 2024-07-09`, latest release v1.3.4 tagged 2024-06-07 (checked via `gh repo view`/`gh release list` 2026-07-16) — no commits or releases in ~2 years as of this survey. Not archived, but effectively unmaintained-in-practice. Generic "fetch a binary from any GitHub repo's releases" fetcher; per its docs, auto-verifies SHA256 if the release publishes a matching `.sha256`/`.sha256sum` asset, else manual `--verify-sha256` flag. No cosign/Sigstore verification support found. Requires eget already installed by the end user — same "not a vendorable install.sh" caveat as above.

**ubi** (houseabsolute/ubi, https://github.com/houseabsolute/ubi) — Apache-2.0. **VERIFIED actively maintained**: pushed 2026-05-02, latest release v0.9.0 (2026-01-11). Rust program, installs prebuilt binaries from GitHub/GitLab releases generically.
- **VERIFIED, high-value primary source**: open issue houseabsolute/ubi#84 "`ubi` should verify checksums by default" (https://github.com/houseabsolute/ubi/issues/84, opened by maintainer `autarch`, still OPEN, most recent comment 2026-01-25) — **ubi does NOT verify checksums by default, as of this survey.** Maintainer's own reasoning against doing it (2025-01-04 comment): plain checksum verification "doesn't really tell us that much" since it only catches transfer corruption, not tampering; *"A much more useful thing to check would be whether the release matches a cryptographic signature. But AFAICT, most projects don't publish this sort of thing. Of the projects above, only `goreleaser` does this. They publish a `checksums.txt` file along with a `checksums.pem` file (the cert used to sign), and a `checksums.sig` file (the signature). This is all done using cosign... verifying the checksum along with verifying the signing of the checksums file provides a much stronger guarantee."* **This is a named, dated, primary-source endorsement — from the maintainer of a well-regarded competing tool — that GoReleaser's cosign-signed-checksums approach (i.e., exactly what release-ci already inherits/implements) is recognized as best-in-class in this ecosystem, and that most projects don't even reach that bar.** Directly relevant to the maintainer's "follow established practice" instruction: the established practice ubi's own author points to IS the GoReleaser/cosign pattern release-ci already uses.
- Thread also surfaces (2025-03-15, commenter `scop`): aquaproj/aqua-registry tracks `cosign:` and `slsa_provenance:` metadata per-project for verification (https://github.com/aquaproj/aqua-registry/blob/main/registry.yaml) — i.e. aqua's registry already models "how to verify this specific project," which is closer to what we'd want if we ever registered our tools there, but that's an aqua-ecosystem integration, not a substitute for our own install.sh.
- ubi requires being pre-installed by the user; not a vendorable single-file script either.

**binenv** (devops-works/binenv, https://github.com/devops-works/binenv) — MIT. **VERIFIED very actively maintained**: pushed 2026-07-16 (day of this survey). Declarative multi-tool version manager (like asdf/mise for prebuilt binaries), config-driven per-tool distribution definitions. Same "pre-installed manager, not a vendorable script" caveat. Not dug deeper — lower priority given the framing above; noting existence/activity only.

**cargo-binstall** (cargo-bins/cargo-binstall, https://github.com/cargo-bins/cargo-binstall) — GPL-3.0. **VERIFIED very actively maintained** (pushed 2026-07-16), but **VERIFIED not applicable to Go**: it resolves packages via crates.io metadata + `[package.metadata.binstall]` in `Cargo.toml`; GitHub-release fallback logic is keyed off Cargo/crates.io package identity, not a generic "any GitHub repo" fetcher. No path found for using it against non-Rust/non-crates.io projects. **Ruled out as inapplicable to a Go/GoReleaser project.**

**aqua** (aquaproj/aqua, https://github.com/aquaproj/aqua) — **VERIFIED very actively maintained** (pushed 2026-07-16, 1778 stars, written in Go). `gh repo view` reported `licenseInfo: null` via the GitHub API license-detection field, but a direct fetch of `raw.githubusercontent.com/aquaproj/aqua/main/LICENSE` (2026-07-16) shows it **is MIT-licensed** (Copyright 2021 Shunsuke Suzuki) — the API's null was a detection quirk, not an actual license gap. Declarative CLI version manager + community "aqua-registry" (a separate repo, https://github.com/aquaproj/aqua-registry, PR-based like godownloader's old tree/like Homebrew-core) that already encodes per-project verification metadata (cosign, SLSA provenance) for many popular tools. Same fundamental caveat: consumers must install `aqua` itself first (via its own install.sh/package managers), then declare tools via `aqua.yaml` referencing the registry — this is a package-manager adoption, not a vendorable single-file install.sh for a project that isn't going all-in on the aqua ecosystem. Registering our tools in aqua-registry could be a reasonable *complementary* distribution channel later, but doesn't answer "what do we vendor into the repo root."

**instl.sh** (installer/instl, https://github.com/installer/instl, site https://instl.sh/) — MIT, but **VERIFIED low activity/low adoption**: pushed 2025-02-21 (~17 months stale as of survey date), only 63 GitHub stars. **Confirmed hosted-service architecture**: it's a server that dynamically generates installer scripts per-request (`curl instl.sh/owner/repo | sh`, `iwr -useb instl.sh/owner/repo/windows | iex` for Windows) — **requires instl.sh's own infrastructure to be reachable at install time**, a third party in the trust/availability path even though it presumably fetches the actual binary from the target repo's own GitHub release. Small, thinly-maintained hosted dependency — a real availability/trust risk if adopted as *the* install path (not just a nice-to-have alternative).

**webinstall.dev / webi.sh** (https://webinstall.dev, source https://github.com/webinstall/webi-installers) — **VERIFIED actively maintained** (webi-installers repo pushed 2026-05-28, 2935 stars — much healthier project than instl.sh). **Confirmed hosted-service architecture, explicitly documented**: per webinstall.dev's own FAQ (fetched 2026-07-16), `curl https://webi.sh/toolname | sh` fetches a bootstrap script from webinstall.dev, which then **queries webinstall.dev's own API** with OS/CPU info to get a "customized snippet" resolving the actual download URL — quote: *"webinstall.dev's API transforms release APIs into a common format and is queried with a small amount of system information... to select a compatible release file URL."* The final binary download does come from the project's own GitHub release (good), but **the install flow has a hard runtime dependency on webinstall.dev's API being up** — same third-party-in-the-loop concern as instl.sh, just backed by a healthier/more active project. Projects are added via PR to webi-installers (community templating repo), godownloader-tree-style.

**goblin.run** (hosted at https://goblin.run, source https://github.com/barelyhuman/goblin — a community continuation of the older, slow-moving `gobinaries`/tj project) — MIT, **VERIFIED actively maintained** (pushed 2026-05-17). **Disqualifying architecture for our use case, confirmed**: per its own description, "Golang binaries compiled on-demand for your system" — goblin.run **recompiles your Go source from scratch on ITS OWN third-party infrastructure at request time**, rather than serving your GoReleaser-built, checksummed, cosign-signed release artifacts. This is not just "a third-party service reachable at install time," it's **a third party rebuilding your binary outside your supply chain entirely** — it bypasses GoReleaser, cosign/Fulcio signing, and SLSA attestation altogether, since the artifact a user gets was never produced by release-ci's pipeline. Clean, definitive disqualifier — flag this explicitly if anyone suggests it.

## FINAL SYNTHESIS AND RECOMMENDATION

### Answering the top-line question: is this solved? Mostly not, in the specific shape release-ci needs.

- The one tool that was purpose-built for exactly this (godownloader) is dead and its maintainer publicly doubted its own approach before killing it.
- GoReleaser itself was asked, by its own users, to build a native replacement in 2019 (issue #1197) and again in 2024 (issue #4565, filed by a user, "goreleaser creates shell scripts like godownloader and publishes them"). The 2024 issue is STILL OPEN as of its last comment (2025-03-11), with caarlos0 acknowledging he's wanted to do it "since godownloader was created" but hasn't gotten to it, and go-task's maintainer confirming in the same thread that go-task **still runs the frozen, unmaintained 2021-era godownloader output** in production today. **This is the strongest single finding: the maintainer of the two most relevant reference projects (GoReleaser itself, and go-task, a mature Go CLI with a real install.sh) both confirm, in their own words, that nothing better exists — go-task hasn't migrated to anything, and GoReleaser hasn't shipped the fix its own maintainer says he's wanted for 6+ years.**
- Every hosted "just point curl at our service" option (instl.sh, webinstall.dev, goblin.run, the old install.goreleaser.com) either (a) is thinly maintained/low-adoption (instl.sh: 63 stars, 17 months stale), (b) introduces a third party in the install-time trust/availability path that release-ci explicitly doesn't want, or (c) in goblin.run's case, actively defeats the entire point of release-ci's cosign/SLSA pipeline by recompiling from source on someone else's infrastructure instead of serving your signed artifacts.
- Every "generic binary fetcher" (eget, ubi, binenv, aqua) requires the *end user* to already have that tool installed — none of them are a thing a maintainer vendors into their own repo root for a bare `curl -fsSL .../install.sh | sh`. They answer a different question ("how do I fetch lots of different tools once I have a manager") not release-ci's question ("what do gostow/hud/dstow/dot-dagger ship at their own repo root").
- **dist (axodotdev)** is the one real, actively-maintained, well-engineered generator that's philosophically closest — no third-party service at install time, automatic checksum verification since v0.26.0, generic (non-Rust) language support via `build-command`. But: it is not Go-verified in practice (only C/Obj-C/JS examples found in official docs), its installer is a *versioned release artifact regenerated every release* rather than a single stable vendored file at a fixed repo path, it has no native `--force`/idempotent-presence-check/`--version` runtime flag (version selection happens by picking a different release's installer URL, not a flag on one script), and adopting it means bringing in an entire Rust-toolchain-based release tool to run alongside GoReleaser just to get an install script — a heavier dependency than release-ci's own footprint for the value gained.
- One piece of independent validation worth weighting heavily: in a live 2025-2026 GitHub issue thread (ubi#84), the maintainer of a competing, actively-maintained installer tool (ubi) explicitly says plain checksum verification is weak, that verifiable-signature schemes are what actually matter, that **"most projects don't publish this sort of thing,"** and singles out **GoReleaser's cosign-signed-checksums pattern as the one exception that does it right** — which is exactly release-ci's own existing model (mandatory checksum + opportunistic cosign). That's an outside, dated, primary-source confirmation that release-ci's planned approach already matches what the ecosystem's best practitioners consider the bar, not something invented in a vacuum.

### Recommendation: (d) write from scratch — but this is a "clear to build," not a "reluctant default." Steal liberally from named, license-compatible sources; do not attempt to wholesale-adopt or generate-from anything found.

Concretely:
1. **Don't adopt any candidate wholesale.** None fit the vendored-single-file, no-third-party-service, Go/GoReleaser-native, presence-check/`--force`/`--version`-flag requirements simultaneously. dist comes closest but drags in a whole second release-tooling stack for a script; the hosted services either compromise the trust model or the supply chain; the generic fetchers solve a different problem.
2. **Don't try to generate from an existing generator.** godownloader (the only tool built for literally this) is dead with no successor, and GoReleaser's own maintainer has wanted to build the successor since 2019 without shipping it — six years of "not solved yet" is itself the answer.
3. **Steal structure/technique, not code wholesale, from:**
   - **golangci-lint's `install.sh`** (https://github.com/golangci/golangci-lint/blob/master/install.sh) — the most directly comparable artifact: a hand-maintained, still-in-production, godownloader-lineage script for a real Go CLI tool, embedding the `client9/shlib` portable-POSIX-shell functions (OS/arch detection, tar/checksum helpers) under their MIT-style notice (verify `client9/shlib`'s `LICENSE.md` text directly before lifting code verbatim, but the ecosystem convention is permissive/attribution-friendly). This is the best "read this before writing ours" reference for POSIX-shell portability idioms (uname normalization, `install -d`, safe tmpdir handling, "wrap destructive ops in one function so a truncated curl|sh can't half-install").
   - **dist's shell installer** (https://axodotdev.github.io/cargo-dist/book/installers/shell.html and an actual generated example, e.g. dist's own `https://github.com/axodotdev/cargo-dist/releases/latest/download/cargo-dist-installer.sh`) — worth pulling an actual generated script to study its embedded-checksum-then-validate-before-unpack flow (their v0.26.0+ behavior) and its env-var-driven install-dir override pattern, as a model for "how does a modern, actively-maintained generator structure this."
   - **release-ci's own existing GoReleaser cosign/checksum pipeline** — per the ubi#84 thread, this is already regarded externally as the gold-standard verification pattern; the install.sh's job is just to *consume* that (verify checksums.txt against its cosign signature, matching what GoReleaser's own `.goreleaser.yml` already produces) rather than to invent new crypto.
4. **Explicit requirements not covered by anything surveyed** (so must be written fresh regardless of what's reused): presence-check exiting 0 when already installed at the target version, `--force`, `--version vX.Y.Z` as a flag (not a different URL), `~/.local/bin` default install dir, and being a single stable-path vendored file rather than a per-release artifact. None of dist, godownloader-descendants, eget, ubi, binenv, aqua, or the hosted services combine all of these; this combination appears to be genuinely novel to release-ci's requirements, not an oversight of not looking hard enough.
