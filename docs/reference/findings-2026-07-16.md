# What we learned — installer, tooling, and pipeline research

Date: 2026-07-16. Companion to the three external surveys in this directory; this one
records **what we verified ourselves**, against our own repos and against primary sources.
The surveys are the reading; this is the evidence and the conclusions.

Decisions these fed are in [`../DESIGN.md`](../DESIGN.md) (D1–D15); open questions are
Q1–Q12 there.

## How to read this

Every claim is tagged:

- **VERIFIED** — checked directly at the source, in this session: a command run, a file
  diffed, an API queried, a script executed. Reproducible from the method given.
- **SOURCED** — taken from a survey that cited a primary source, not independently re-run.
- **INFERRED** — reasoning over verified facts. Judgement, and marked as such.

Nothing here is unattributed. **Three separate documents in this org have now asserted
cross-repo "identical/both/all" claims that failed on inspection** (§7), so the tagging
is not ceremony.

## 1. The installer problem is genuinely unsolved upstream

**The finding**: nothing to adopt. We build. → `DESIGN.md` D4.

**godownloader is the closest historical match and it is dead.** GoReleaser's own project
generated an `install.sh` *from* a `.goreleaser.yml` — almost exactly our ask.
**VERIFIED** ([repo](https://github.com/goreleaser/godownloader)): archived 2022-01-14,
read-only, README reads *"Warning: this is no longer actively maintained."* **No successor
is named.**

**Why it died matters more than that it died.** **VERIFIED** via
[godownloader#161](https://github.com/goreleaser/godownloader/issues/161) (caarlos0,
GoReleaser's author, 2019-11-20) — he did not merely run out of time
(*"I honestly barely make the time to maintain nfpm and goreleaser"*). **He doubted the
approach**:

> "At this point, I'm not even sure the way we're handling this was a good idea."
> "Maybe it would be better to make this a pipe on goreleaser?"

**That pipe was never built.** **VERIFIED** via `gh api` against
[goreleaser#4565](https://github.com/goreleaser/goreleaser/issues/4565) — "Integrating
godownloader into goreleaser", opened 2024-01-22, **still open**, assigned to caarlos0,
3 comments:

> **caarlos0**, 2024-01-29: *"this is something I've been wanting to do for a while (since
> godownloader was created, actually). but yeah, I need to do it eventually…"*
>
> **andreynering** (go-task maintainer), 2025-03-11: *"We still rely heavily on
> godownloader for Task, despite being deprecated. Having this integrated officially would
> be awesome."*

*(WebFetch could not render these comments — the API was needed. Worth knowing for future
verification passes.)*

**The hosted service is gone.** **VERIFIED**: `install.goreleaser.com` returns NXDOMAIN;
`curl` cannot resolve it. Any sibling doc still referencing that URL is stale.

**The ecosystem froze rather than migrated.** **SOURCED**
([tooling survey](installer-tooling-survey-2026-07-16.md)): go-task still ships the frozen
2021-era generated script; golangci-lint detached from the dead generator in Feb 2024 but
**kept the generated output**, still embedding `client9/shlib` verbatim, now hand-maintained.
Nobody moved to a replacement — there wasn't one.

**Every candidate fails a checkable test** (**SOURCED**, same survey):

| candidate | why it fails |
|---|---|
| **`dist`** (ex-cargo-dist) | Closest philosophically, **and actively maintained** — released into mid-2026, Apache-2.0. But its installer is a **per-release regenerated artifact**, not a stable vendored file; no presence-check, `--force`, or `--version`; adopting it imports a whole Rust release tool |
| **instl.sh**, **webi** | Require **a third party reachable at install time** — a different trust and availability model from a script in our own repo |
| **goblin.run** | **Recompiles your Go source on its own servers** rather than serving your signed artifacts. Would defeat the entire cosign/SLSA chain |
| **ubi**, **aqua**, **binenv**, **cargo-binstall** | All require the user to pre-install a manager first ⇒ none serve the fresh-machine case. (eget is ~2yr stale; cargo-binstall is crates.io-only) |

**INFERRED**: nothing surveyed combines presence-check + `--force` + `--version` + a
stable vendored file + no install-time third party. That combination looks **unserved
rather than deliberately avoided**.

**The honest counter-argument, recorded** (**INFERRED**): what caarlos0 doubted was
*generating* installers from build config. We propose no generator — one hand-written
script with a config block ([`DESIGN.md` §6.3](../DESIGN.md)). That's a smaller claim than
his, and the objection doesn't reach it. But it *does* mean the burden is on us, and it's
why D6 forbids a template engine outright.

**Outside corroboration** (**SOURCED**): ubi's maintainer, in
[ubi#84](https://github.com/houseabsolute/ubi/issues/84), names GoReleaser's
cosign-signed-checksums as the pattern the ecosystem gets *right* — i.e. what release-ci
already produces is what these tools want to consume.

## 2. External conventions: what's real, and what was our habit

**The finding**: three of our "conventions" were local habit. → D8, D10, D11, `DESIGN.md` §6.8.

**SOURCED**: [conventions survey](installer-conventions-survey-2026-07-16.md), 15
installers read at source (rustup, Homebrew, Docker, Deno, Bun, uv, Starship, nvm, fnm,
Volta, Atuin, mise, k3s, Helm, golangci-lint/go-task).

**What is genuinely universal**: exactly one thing — **errors and warnings go to stderr**.
That's it.

**What is NOT a convention** (we assumed several of these were):

| we assumed | reality |
|---|---|
| `INSTALL_DIR` is a normal spelling | **Nobody** exposes a bare, unprefixed install-dir env var. It's always tool-scoped: `UV_INSTALL_DIR`, `MISE_INSTALL_PATH`, `HELM_INSTALL_DIR`, `INSTALL_K3S_BIN_DIR`, `NVM_DIR`, `BUN_INSTALL`, `VOLTA_HOME`, `DENO_INSTALL`. **VERIFIED** by grepping the saved sources: no match for a user-facing bare `INSTALL_DIR` in any of the 15 → **D8** |
| `XDG_BIN_HOME` is the XDG-correct norm | Honoured by **exactly one** tool: **uv**. **VERIFIED** — grep across all 15 sources matches only `uv.sh`. We follow uv specifically, not an ecosystem norm |
| `~/.local/bin` is the common default | **2 of 15.** Most use a tool-specific dir (`~/.cargo`, `~/.deno`, `~/.bun`, `~/.nvm`, `~/.volta`); system tools use `/usr/local/bin`; golangci-lint/go-task use a *relative* `./bin` |
| info output goes to stdout | **Split, not settled.** The survey originally called this *"the one true, unanimous convention"* — **falsified**: mise routes `info()` to stderr (**VERIFIED**, `mise.run:20` — `info() { echo "$@" >&2; }`), and Volta does the same. Corrected in the survey's reviewer's note |
| presence-checking is normal | **5 of 15.** Most installers overwrite unconditionally — "idempotent by brute force" rather than by detection |
| exit-quietly-when-present is our contract | **Fully-silent presence-exit is attested nowhere.** Every checking installer *speaks*. This **vindicates** our "speaks, exit 0" rule; `--silent` is our own extension |

**mise is our closest precedent** and independently arrived at our contract. **VERIFIED**
by fetching `https://mise.run`:

- `mise.run:282` — `install_path="${MISE_INSTALL_PATH:-$HOME/.local/bin/mise}"` (our default)
- `mise.run:289-297` — `MISE_INSTALL_SKIP_IF_EXISTS` → `info "…skipping install"; return 0` (**speaks, exits 0** — our F1)
- `mise.run:122` — `error "mise install requires shasum or sha256sum but neither is installed. Aborting."` (our F4, mandatory checksum, hard abort)
- `mise.run:15` — `MISE_QUIET` makes `info()` a no-op while the exit code is untouched (our F6, level-vs-exit-code split)

**The one place mise contradicts dstow's B6** (**VERIFIED**, `mise.run:286-288`), quoted
because it's now open question **Q1**:

> "Only the install path is checked (not the wider PATH) so that skipping never leaves
> install_path missing."

**Missing-verifier behaviour is a genuine ecosystem split** (**SOURCED**), worth knowing
we picked a side: mise, Helm, golangci-lint and go-task **abort**; **uv skips and
proceeds**. We abort (F4) — the larger and safer camp, but not unanimous.

## 3. Our two installers diverge more than anyone believed

**The finding**: the sibling survey's central claim about our own scripts is wrong. → D12.

**VERIFIED** by normalized diff (`sed 's/gostow/TOOL/g'` vs `sed 's/dot-dagger/TOOL/g'`),
`gostow/install.sh` (221 lines) against `dot-dagger/install.sh` (186 lines):

The [dstow survey §2.1](https://github.com/rocne/dstow/blob/main/docs/reference/release-installer-survey-2026-07-14.md)
asserts dot-dagger's is *"essentially the same script minus the man page/completions
block."* **It ran no diff.** There is a **second, structural divergence** — in the argument
parser:

| | gostow | dot-dagger |
|---|---|---|
| tool identity | `TOOL="gostow"` **baked** (`:30`) | optional **positional**, defaults to `dotd` (`:24,27`) |
| unknown positional | **error** — `*) printf 'error: unknown argument'` (`:53`) | accepted as the tool name, validated against `VALID_TOOLS` (`:46-63`) |

**INFERRED**: baked-slug (dstow's B4) is **gostow's** shape, not dot-dagger's. dot-dagger's
positional is **dead generality** — `VALID_TOOLS` has exactly one entry. Drop it.

**A latent bug we must not inherit** (**VERIFIED**, `dot-dagger/install.sh:61`):

```sh
printf 'error: unknown tool %q. Valid tools: %s\n' "$TOOL" "$VALID_TOOLS"
```

**`%q` is not POSIX `printf`.** It misbehaves under `dash` — which is exactly what
`curl … | sh` invokes on Debian/Ubuntu. A bug on the error path of the script whose whole
job is being safe to pipe into `sh`.

**What both already do that contradicts B6** (**VERIFIED**): *both* implement
`INSTALL_DIR="${INSTALL_DIR:-$HOME/.local/bin}"` **and** a `--dir` flag —
`gostow:36,46`, `dot-dagger:31,40`. dstow's B6 calls `~/.local/bin` a *contract* the
snippet hardcodes, i.e. non-overridable. **Neither shipped consumer honours that.**
Tunability is the two-consumer precedent → **D9**, and `--dir` keeps its name → **D11**.

**Worth keeping** (**VERIFIED**, both): `--help` prints the script's own comment header via
`sed -n '2,23p' "$0" | sed 's/^# \?//'`. Good idiom.

## 4. The consumer census, measured

**The finding**: two long-standing claims about consumers are false. → `DESIGN.md` §1, Q8.

**VERIFIED** 2026-07-16 (`grep -rl 'rocne/release-ci/.github/workflows/release.yml@'`,
`gh release list`, file existence):

| repo | consumes release-ci | releases cut | `install.sh` | version-guard files |
|---|---|---|---|---|
| dot-dagger | 2 workflows | **100** (v0.11.0) | yes | **0** |
| gostow | 2 workflows | 5 (v0.4.0) | yes | **3 files / 4 sites** |
| hud | 2 workflows | **0** | no | 0 |
| dstow | 2 workflows | 0 | not yet | 0 |
| sorta | **0** | 2 | no | 0 |

**All 8 references pin `@v0.1.1`** — uniformly, no drift. But **VERIFIED**: `v0.1.1` is
release-ci's **only tag ever cut**. Tag discipline is *untested*, not proven → **Q12**.

**Two corrections this forced:**

1. **hud has never released.** It is a *configured* consumer, not a proven one. Its
   root-level `.goreleaser.yaml` — the layout outlier that constrains absorption designs
   in #3 — **has never been exercised by release-ci**. And its missing `install.sh` is
   almost certainly *not yet* rather than *declined*: a repo with no releases has nothing
   to install. Earlier text treated that absence as a deliberate opt-out and as evidence
   for the opt-out doctrine. **Withdrawn** → **Q8**.
2. **The version guard exists in exactly one consumer.** Both issue #2's original body and
   the [dstow survey §1](https://github.com/rocne/dstow/blob/main/docs/reference/release-installer-survey-2026-07-14.md)
   claim *"both gostow and dot-dagger"* have a hand-rolled refuse-v1.0.0 guard.
   **VERIFIED false**: grep of dot-dagger's entire `.github/` and its
   `release-please-config.json` for `version-guard|refuse|1.0.0` returns **zero hits**.

**The duplication is intra-gostow, not inter-consumer** — 4 sites, each with a distinct
documented reason, and **only 2 are absorbable**:

| site | layer | absorbable? |
|---|---|---|
| `ci.yml:27` | manifest version on ordinary PRs | **No** — release-ci isn't in the picture |
| `release-please.yml:42` | the release PR itself | **No**, and it's load-bearing: GitHub doesn't trigger `pull_request` workflows for PRs opened with `GITHUB_TOKEN`, so *"the release PR — the one PR whose version actually matters — arrives with zero checks"* |
| `release-please.yml:67` | last line before the release-ci call | **Yes** |
| `release.yml:23` | same, break-glass tag-push path | **Yes** |

**INFERRED**: the case for absorption is *2 of 4 sites, in 1 of 4 consumers, and gostow
keeps the other two regardless.* The "copy-paste policy in every consumer" premise that
motivated #2 **does not exist**. What survives is narrower and honest: sites 3–4 are the
last line before the irreversible publish.

**Also noted** (**VERIFIED**): **sorta has 2 releases but consumes release-ci zero times**
— it releases without the pipeline. Previously described only as "conventions, not the
pipeline," which understates it: it is a repo that releases by other means. Whether that's
a gap or correct is a #3 question nobody has asked.

**The versioning config, verified**: gostow, dot-dagger and hud **all three** set
`"bump-minor-pre-major": true` and `"bump-patch-for-minor-pre-major": false`. Flipping the
second implements the pre-1.0 downshift exactly — one line, three repos (#8). dstow sets
neither and is out of scope: `"initial-version": "1.0.0"`.

## 5. mise works against our releases today — tested, not theorized

**The finding**: a free distribution channel that consumes the provenance we already emit.
→ D13, #7.

The [mise survey](mise-survey-2026-07-16.md) reached this by reading ubi's matching regexes
and **explicitly flagged it as untested**, recommending a smoke test before documenting it.
So it was run. **VERIFIED**, mise 2026.7.7, against real releases:

```
$ mise install github:rocne/gostow@0.4.0
mise github:rocne/gostow@0.4.0 [1/3] download gostow_v0.4.0_linux_amd64.tar.gz
mise github:rocne/gostow@0.4.0 [2/3] checksum gostow_v0.4.0_linux_amd64.tar.gz
mise github:rocne/gostow@0.4.0 [2/3] verify GitHub artifact attestations
mise github:rocne/gostow@0.4.0 [2/3] ✓ GitHub artifact attestations verified
mise github:rocne/gostow@0.4.0 [3/3] extract gostow_v0.4.0_linux_amd64.tar.gz
mise github:rocne/gostow@0.4.0 ✓ installed

$ gostow --version
gostow 0.4.0 (GNU Stow 2.4.1 compatible)
```

**Zero config, zero registry entry — and it verified the attestations this pipeline
emits.**

Three things only running it revealed:

1. **It picked the right asset over competing `.deb`/`.rpm`**, which carry the same
   `amd64`/`x86_64` tokens (a real gostow release ships `gostow-0.4.0-1.x86_64.rpm`,
   `gostow_0.4.0_amd64.deb`, *and* `gostow_v0.4.0_linux_amd64.tar.gz`). The desk research's
   regex analysis had not considered that collision — the paper claim could easily have
   been wrong.
2. **dot-dagger@0.5.2 installs clean too, but verifies SLSA provenance rather than artifact
   attestations.** Our two consumers exercise **different verification paths**. Both work;
   nobody knew they differed.
3. **The backend resolved dot-dagger's repo/binary name mismatch** (`dot-dagger` → `dotd`)
   unaided.

**INFERRED, and the point**: our pipeline already produces SLSA attestations and
cosign-signed checksums, and **almost nothing on the install path consumes them** —
`install.sh` checks checksums and treats cosign as opportunistic. mise's `github` backend
verifies **by default, unprompted**. This is our existing security work finally being used.

**What it is not**: a replacement for `install.sh`. **INFERRED** from **VERIFIED** fact —
mise is itself a binary something must install (its own action downloads a mise binary), so
on a genuinely fresh machine there is no mise either. `curl | sh` has no prerequisite. The
bootstrap ordering runs **opposite** to the naive "mise replaces the installer" take.

**Backend choice** (**SOURCED**): use `github` — no registry entry, matches our asset names,
verifies natively. **Never `go:`** — it builds from source, needs a toolchain, and
**silently discards the entire signed-release pipeline**. A bare `mise use -g gostow` short
name isn't realistic: mise's registry has a "reasonably popular" bar our tools won't clear.

## 6. Our own supply chain has a hole, and the obvious fix doesn't close it

**The finding**: → #4, Q5.

**VERIFIED**, `.github/workflows/release.yml:89`:

```yaml
      - name: Install Cloudsmith CLI
        run: pipx install cloudsmith-cli
```

**No version pin.** At the moment this resolves, the job **already holds**
`GPG_PRIVATE_KEY` (written to disk at `:80-86`, *before* this step), `CLOUDSMITH_API_KEY`,
`HOMEBREW_TAP_GITHUB_TOKEN`, `contents: write`, and `id-token: write` for OIDC.

**INFERRED**: this pipeline's entire product is provenance — we attest what we build,
cosign-sign the checksums, re-verify post-publish — and then publish using a tool whose own
provenance we never established.

**The obvious fix is insufficient, which corrects our own first proposal.** **VERIFIED**
against [PyPI's API](https://pypi.org/pypi/cloudsmith-cli/json): `cloudsmith-cli` 1.19.0
declares **17 dependencies, nearly all open ranges** —

```
click!=8.3.0,>=8.1.8   keyring>=25.4.1        requests>=2.18.4
cloudsmith-api<3.0,>=2.0.25   PyJWT[crypto]>=2.0.0   requests_toolbelt>=1.0.0   …
```

Only **2 of 17** (`mcp==1.27.2`, `python-toon==0.1.2`) are exact-pinned upstream. **pip
resolves the rest fresh on every run**, so `pipx install 'cloudsmith-cli==X.Y.Z'` pins the
top level and **leaves the transitive tree — `requests`, `keyring`, `PyJWT[crypto]`, all
with crypto/network reach — wide open.** That is where a supply-chain attack lands.

**What actually closes it**: `--require-hashes` with a compiled, fully-resolved
requirements file (`pip-compile --generate-hashes`). An earlier revision of #4 dismissed
this as over-engineering; that was wrong.

**mise does not close it either — correcting the mise survey's own headline.**
**SOURCED**: mise's lockfile gives the **`pipx` backend version-only support — no
checksum, no provenance**. So mise pins the version we can already pin and doesn't verify
the tree. Its one unique contribution here is **`minimum_release_age`** (24h default),
which **does** forward to transitive resolution for `pipx` specifically — a time-based
quarantine on freshly-published dependencies. Different axis from hashes (time, not
identity); **composes with them, doesn't replace them**.

**INFERRED, unresearched → Q5**: the bigger win may be deleting the dependency. If
GoReleaser's publisher `cmd` can `curl` Cloudsmith's HTTP API directly, all 17 packages
and their transitives leave the signing job entirely.

## 7. The prior art is unreliable — treat this as standing

**The finding**: → D14, `DESIGN.md` §4 and §8.5.

The [dstow release-installer survey](https://github.com/rocne/dstow/blob/main/docs/reference/release-installer-survey-2026-07-14.md)
is cited as prior art by issues #1, #2 and #3. **Two of its claims were checked. Both were
wrong** (§3 and §4 above):

1. *"dot-dagger/install.sh is essentially the same script minus the man page/completions block"* — a diff shows a second structural divergence. It ran no diff.
2. *"both gostow and dot-dagger have a hand-rolled 'refuse v1.0.0+' guard"* — dot-dagger has none.

**Its scope is also narrower than its citations imply** (**SOURCED**): it surveyed only
release-ci, gostow, dot-dagger and dstow. **It never examined hud or sorta**, and never
mentions `release-dryrun.yml` or `pr-title.yml` — two of #3's own audit candidates. There
is no prior art on those.

**This is not one bad document.** In this session:

- dstow's `DESIGN.md` §9 advertises requirements **"B1–B9"**; **B7 and B9 were never
  written into it** — they exist only in the [dstow#28](https://github.com/rocne/dstow/issues/28)
  ledger. (**VERIFIED**; neither touches release-ci, so no harm — but the gap cost real
  time to establish.)
- The **conventions survey** we commissioned called info-to-stdout *"the one true,
  unanimous convention"* — **falsified** by its own closest precedent (§2).
- The **tooling survey** corrected a **false premise in its own brief** (we told it
  axodotdev had wound down; `dist` is actively maintained). The correction is the agent's,
  and it was right.

**The rule**: *verify before citing.* Structural descriptions in these documents have held
up well; **cross-repo comparative claims have not**. The cheap tell is a sentence
containing "identical", "both", "all", or "every" about more than one repo.
