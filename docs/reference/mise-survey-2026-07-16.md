### Config file — VERIFIED
Source: https://mise.jdx.dev/configuration.html (fetched 2026-07-16)
- Canonical filename: `mise.toml`. `mise.local.toml` is for local (gitignored) overrides and takes priority.
- Search order (top overrides bottom... actually doc says "earlier files overriding later ones", need to double check precedence direction on re-read): `mise.local.toml`, `mise.toml`, `mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`, `.config/mise/conf.d/*.toml`.
- Dotfile variants allowed: `.mise.toml`, `.mise/config.toml` (paths starting with `mise` can be dotfiles).
- System config: `/etc/mise/config.toml`; user global: `~/.config/mise/config.toml`.
- `[tools]` syntax:
  ```toml
  [tools]
  node = '24'
  python = '3.12'
  go = { version = "22", postinstall = "corepack enable" }
  ```
- Version pinning forms: exact (`'20.0.0'`), fuzzy (`'3'`), `'latest'`, VCS ref (`'ref:master'`), prefix match (`'prefix:1.19'`), local path (`'path:./shfmt'`), `'lts'`, subtraction (`'sub-2:lts'`).
- CONFIRMED precedence direction directly from source (`gh api .../docs/configuration.md`, fetched 2026-07-16): "in order of precedence, top overrides configuration of lower paths" — i.e. `mise.local.toml` (listed first) overrides `mise.toml`, which overrides `mise/config.toml`, etc. down to `.config/mise/conf.d/*.toml` (lowest of that same-directory list). Separately, directory-tree walking means a project's own `mise.toml` overrides a parent directory's `mise.toml` (configs "recurse upwards" and merge, more-specific wins). Doc explicitly points to `LOCAL_CONFIG_FILENAMES` in `src/config/mod.rs` as the authoritative source if precedence questions arise ("Some legacy paths are not listed here for brevity" — i.e. the docs page itself admits it's not 100% exhaustive).
- `.mise.toml` (leading dot, no directory) IS still valid: confirmed verbatim "Paths which start with `mise` can be dotfiles, e.g.: `.mise.toml` or `.mise/config.toml`" — treated as an equivalent dotfile form of the same canonical names, not flagged deprecated/legacy in this doc.

### http backend — VERIFIED (exists)
Source: https://mise.jdx.dev/dev-tools/backends/http.html (fetched 2026-07-16)
- Exists. Points at arbitrary HTTP(S) URLs for binaries/archives.
- Syntax: `mise use -g http:my-tool[url=https://example.com/releases/my-tool-v1.0.0.tar.gz]@1.0.0`

### houseabsolute/ubi asset-matching algorithm — VERIFIED FROM SOURCE (raw README.md, houseabsolute/ubi @ master, fetched 2026-07-16)
This is the underlying tool that mise's `ubi` backend wraps.
- Step 1 — extension allowlist filter: recognizes `.7z`, `.AppImage` (Linux only), `.bat`/`.exe` (Windows only), `.bz2`, `.bz`, `.gz`, `.jar`, `.phar`, `.py`, `.pyz`, `.sh`, `.tar.bz2`, `.tar.bz`, (truncated in my grep but doc lists more) `.zip`, `.zst`, and **no extension**. It's careful about dots-that-aren't-extensions, explicitly citing `some-tool.linux.amd64` and `some-tools-linux-x86-64-1.3.5.tar.gz` as examples it handles correctly.
- Step 2 — if only one asset survives extension filtering, it's picked automatically (assumes single-platform or platform-agnostic release).
- Step 3 — OS filter: regex match against filename for Linux/macOS/Windows/FreeBSD etc.
- Step 4 — arch filter: regex match for x86-64/ARM64/PowerPC etc.
- Step 5 — musl-libc filter (Linux only, only if the *running* system is musl): prefers files indicating musl if a libc indicator is present; if no libc indicator present in filename, the asset is still included (not excluded) but musl-indicated assets are preferred over unmarked ones when both exist.
- Step 6 — tie-breaking preferences: prefer 64-bit over 32-bit on 64-bit platforms; apply user-supplied `--matching` substring filter if given; prefer ARM64 over x86-64 specifically on macOS-ARM64 hosts.
- Step 7 — final tiebreak: alphabetical sort, pick first (deterministic).
- Archive-internal executable lookup: looks for exact filename match to project name (or `--exe` override) first; if not found, looks for a file that **starts with** the project name (handles names like `precious-linux-amd64`) — but on Unix, partial matches are only considered if the file has the executable bit set.
- Extra flag of note: `--min-age-days` — "Minimum age in days for releases... useful for mitigating supply chain attacks... especially useful for projects that use GitHub's immutable releases feature." (Direct analog to mise's own `minimum_release_age` setting documented above — defense in depth at both the ubi and mise level.)
- **Applied to our asset name `gostow_v0.2.0_linux_amd64.tar.gz`**: `.tar.gz` passes the extension filter; `linux` is a standard OS token; `amd64` is a standard arch token. This is a textbook-compatible shape — VERIFIED as matching ubi's documented algorithm (no ambiguity: single OS token, single arch token, standard tar.gz extension, no competing libc variants to worry about unless we also ship musl builds). The leading `v` in `v0.2.0` is part of the version component, not part of the OS/arch matching pass, so it doesn't interfere.
- CONCLUSION for Q2 ubi question: **YES, `mise use -g ubi:rocne/gostow` (or `ubi:rocne/dot-dagger`, etc.) would work TODAY against our current GoReleaser-default-style asset names, with zero registry entry required**, provided (a) there's exactly one linux/amd64 (etc.) asset per platform combination (no ambiguous duplicates) and (b) the binary inside the tar.gz is named `gostow` (matches repo name) or we pass `--exe`/`exe = "..."` if it differs.

### ubi OS/arch regex — VERIFIED FROM SOURCE (ubi/src/os.rs, ubi/src/arch.rs, houseabsolute/ubi @ main, fetched 2026-07-16)
Read the actual Rust regexes, not just the README prose:
- `macos_re`: `(?i:(?:\b|_)(?:darwin|mac(?:osx?)?|osx)(?:\b|_))` — **explicitly matches "darwin"** (case-insensitive), so GoReleaser's default `.Os` value for macOS (which is literally `darwin`) is correctly recognized by ubi. No renaming needed for Mac builds.
- `linux_re`: matches `linux` (with optional `static` suffix, for pkg-built binaries) — our `linux` token matches directly.
- `x86_64_re` (used to match the "amd64" arch token): includes literal alternatives `386 | i586 | i686 | x86[_-]32 | x86[_-]64 | x64 | amd64 | linux64 | win64` — **`amd64` is explicitly and literally one of the recognized tokens.** Confirms our `_amd64` filename component matches directly, no translation needed.
- This fully and concretely confirms (not just plausibly, but by reading the matcher regex) that `gostow_v0.2.0_linux_amd64.tar.gz` is matched correctly by ubi's OS and arch filters with zero configuration.

# SYNTHESIS

## Q1 answer: mise inside CI — honest assessment

**Case for adopting mise in CI:**
- Replaces 4 separate install mechanisms (`actions/setup-go`, `sigstore/cosign-installer`, `pipx install cloudsmith-cli`, `goreleaser/goreleaser-action`) with one `jdx/mise-action` step + one `mise.toml`. VERIFIED all four of our current tools have a real backend: go = `core:go`, goreleaser/cosign = `aqua` (registry-confirmed entries), cloudsmith-cli = `pipx:cloudsmith-cli` (no short name, but works). golangci-lint/shellcheck also have confirmed `aqua` registry entries if/when we add linting to this pipeline.
- **Single source of truth for versions.** Right now each tool's version is pinned in a different place/format: `actions/setup-go@v6`'s `go-version:` input, `cosign-installer@v3`'s implicit/pinned version, `goreleaser-action@v7`'s `version:` input, and cloudsmith-cli's implicit "whatever pipx grabs as latest" (no explicit version pin visible in the grep — a real gap today: `pipx install cloudsmith-cli` with no `==` pin is NOT reproducible run-to-run). mise centralizes all of this into one `mise.toml`/`mise.lock` pair.
- **Reproducibility is real and lockfile-backed**, not just "same file used twice": VERIFIED `mise.lock` gives full version+checksum+URL (and for aqua/github backends, cryptographically-verified provenance type: slsa/cosign/minisign/github-attestations) pinning, generated once (`mise lock`) and consumed identically by `mise install` locally and in CI. `MISE_LOCKED=1`/`locked=true` makes CI fail closed if anything isn't pre-resolved in the lockfile — stronger reproducibility guarantee than what we have today (today, an unpinned `pipx install cloudsmith-cli` could silently pick up a new cloudsmith-cli version on any given CI run).
- **Genuine supply-chain features beyond what we have today**: `minimum_release_age` (default 24h delay before mise will install a brand-new release — mitigates "malicious release published moments ago" attacks) and ubi's own analogous `--min-age-days`. - **CI-native trust handling**: VERIFIED mise auto-trusts config in detected CI environments (no interactive prompt), so adopting it doesn't add a manual `mise trust` step to the pipeline.
- **Caching**: mise-action has built-in GHA caching (default on), comparable to what `actions/setup-go` already gives us for Go specifically, but extends the same caching to goreleaser/cosign/cloudsmith-cli too (which currently have no explicit caching — `goreleaser-action` and `cosign-installer` may or may not cache internally; not verified either way here).

**Case against / what we'd lose vs. `actions/setup-go`:**
- `actions/setup-go` is GitHub-native, extremely well-trodden, maintained by GitHub itself, and its Go-specific caching (module + build cache, keyed automatically) is purpose-built and very mature — mise's generic caching is unlikely to beat it for the Go toolchain specifically, and we'd be trading a first-party GitHub action for a third-party one for at least the Go piece.
- **New dependency surface**: mise itself becomes a supply-chain link — we'd depend on `jdx/mise-action` (VERIFIED actively maintained: v4.2.0, 2026-06-17, 708 commits, but still a single-maintainer-adjacent project, not GitHub-owned) plus mise's own binary release, plus (if using aqua backend) mise's bundled/live aqua-registry data, plus (if using aqua/github backends) mise's own re-implementation of cosign/SLSA verification logic. That reimplementation is a real thing to trust (VERIFIED: mise ships a "native Rust implementation" of cosign-signature and SLSA-provenance verification specifically so it doesn't need the cosign/slsa-verifier CLIs) — good for portability, but it's now mise's verifier code we're trusting instead of the actual `cosign`/`slsa-verifier` binaries upstream projects publish and that security researchers scrutinize directly. This is a genuine, non-trivial trade-off worth naming rather than hand-waving.
- **`go` backend / core:go tool version resolution semantics differ subtly from `actions/setup-go`'s go-version-file mode** — not independently verified here whether mise's core:go can read `go.mod`'s `go` directive the same way `actions/setup-go`'s `go-version-file: go.mod` does; would need to confirm before treating this as a drop-in replacement.
- **Churn cost**: rewriting a currently-working, already-hardened pipeline (this repo has commits specifically about "pin reusable signer in attestation verify" and "bash-shell smoke" fixes — i.e., this pipeline has already had its sharp edges filed down through real incidents) introduces new sharp edges of its own, purely from unfamiliarity, even if mise is objectively more capable.
- **wings_enabled / mise-wings**: a newer opt-in (default off) paid caching proxy that ties into GitHub OIDC tokens — VERIFIED it exists in the current action.yml, worth being aware of so nobody accidentally turns it on given this pipeline already uses `id-token: write` for its own SLSA/Sigstore purposes (the action's own docs explicitly flag this exact risk).

**Verdict (my synthesis, not a "primary source" claim):** Adopting mise for tool installation in CI is a **plausible, moderate win, not a slam dunk**. The strongest, best-verified case is for the tools that currently have NO explicit version pin and NO lockfile-level reproducibility (cloudsmith-cli via unpinned `pipx install`) — mise's lockfile would concretely close that gap. For Go itself, `actions/setup-go` is mature enough that switching is more about consolidation/consistency than fixing a real deficiency. I'd frame this as "worth a spike," not "obviously required."

## Q3 answer: mise vs. install.sh — bootstrap ordering

- **Yes, there is a real bootstrap-ordering relationship, and it runs the OTHER way from a naive "mise replaces install.sh" take**: mise itself is a binary that must be installed by *something* — VERIFIED mise-action's own action.yml literally downloads a mise binary (with a `sha256` verification input) from GitHub or mise.jdx.dev. On a genuinely fresh machine (dstow's stated bootstrap scenario — "nothing installed"), a user doesn't have mise yet either, so `mise use -g gostow`/`aqua:rocne/gostow`/`github:rocne/gostow` requires mise to already be present. install.sh's `curl | sh` pattern has NO such prerequisite — it's the more primitive, lower-common-denominator bootstrap path.
- **Therefore mise does not obviate install.sh for the fresh-machine case** — it is genuinely complementary, not a replacement, for that scenario specifically. install.sh remains the correct answer to "I have nothing" (which is explicitly dstow's design constraint per the task description).
- **For users who already have mise installed** (a real and growing population, given mise's own popularity as a polyglot version manager), mise support is a strict ADDITIONAL channel — those users get a cleaner, declarative, version-pinned, verifiable install path (`mise use -g github:rocne/gostow` or eventually `aqua:rocne/gostow`) instead of running our shell script. It doesn't change what install.sh needs to do; install.sh keeps doing exactly what it does today for the no-mise case.
- **mise does NOT change what install.sh needs to do** in any technical sense I can find — they operate at different layers (install.sh installs a specific binary; mise is a general-purpose version manager that, once present, can install many things including ours). The only "interaction" is purely about audience overlap: some fraction of our users will have mise already and would prefer using it over `curl | sh`.
- **Recommendation**: (b) — mise support is a **genuine additional distribution channel worth adding**, layered on top of install.sh, not a replacement for any part of it. Concretely: (1) the `github` backend gets us this essentially for free today given our asset-naming already matches GoReleaser defaults (VERIFIED at the regex level) — worth documenting in each tool's README as "if you have mise: `mise use -g github:rocne/<tool>`" with near-zero engineering cost; (2) an aqua-registry submission is a reasonable follow-up for users who want cosign/SLSA verification baked into the install and eventually a shorter mise command, but is not urgent and has an unverified time cost (the `argd s` automation reduces it, but I have not personally run it, so I can't attest to how smooth it actually is in practice — INFERRED-plausible from docs, not independently tested); (3) install.sh should NOT be deprecated or reduced in scope — it remains the only path that requires zero pre-existing tooling, which is exactly dstow's stated bootstrap requirement.

### mise.lock lockfile — VERIFIED FROM SOURCE (docs/dev-tools/mise-lock.md in jdx/mise, fetched 2026-07-16), supersedes earlier WebFetch summary
- **Not automatic.** Lockfiles are not created by default; you must run `mise lock` (or enable `[settings] lockfile = true` and then `mise install`/`mise use`, which will create/update it going forward).
- Purpose stated in docs, verbatim: "Reproducible builds... Security: Verifies tool integrity with checksums when supported by the backend... Version pinning... Avoids API rate limits: By storing download URLs, future installs use the lockfile and do not need to call GitHub (or other providers), avoiding rate limits and the need for GITHUB_TOKEN in most cases."
- Format: TOML, `[[tools.<name>]]` array-of-tables per tool with `version`, `backend`, `options`; per-platform subtables `[tools.<name>.platforms.<os-arch>]` with `checksum`, `size`, `url`.
- **Backend support for lockfile (verbatim tiers from doc):**
  - Full support (version + checksum + size + URL): `aqua`, `http`, `github`, `gitlab`.
    - Of these, **provenance support** (i.e., lockfile records a verified provenance type) is further limited to: `aqua`, `github`, `core:python` (precompiled binaries), `core:ruby` (precompiled binaries), `core:zig` (install-time).
  - Partial (version + URL + provenance): `vfox` (tool plugins only).
  - Partial (version + checksum + size): `ubi`.
  - Basic (version + checksum): `core` (some tools).
  - Version only: `asdf`, `npm`, `cargo`, `pipx`.
  - Doc explicitly says more backends will gain full support "over time" — i.e., this is evolving, not final.
  - **Direct relevance to our tool list**: go = `core:go` (not explicitly one of the core tools called out with provenance support — python/ruby/zig are named, go is not, so go's lockfile entry is likely version+checksum "basic" tier, not provenance-verified — UNCONFIRMED, worth testing). goreleaser/cosign/golangci-lint/shellcheck = `aqua` backend → FULL support including provenance. cloudsmith-cli (no registry entry, `pipx:cloudsmith-cli`) → **version-only** lockfile support, no checksum/provenance tracked by mise for it.
- **Provenance verification mechanics (verbatim, important for our SLSA/cosign question)**: "When mise lock generates a lockfile, it records a verified provenance type (e.g., slsa, cosign, minisign, github-attestations) for each tool when one is available. For the current platform, mise downloads the artifact and performs full cryptographic verification at lock time... This applies to both the aqua and github backends." Cross-platform entries in the lockfile get provenance *detected from registry metadata without verification* (not runnable on the lock-time machine).
- By default `mise install` with a lockfile containing checksum+verified-provenance TRUSTS the lockfile and skips re-verification (avoids redundant GitHub API calls / rate limits). Force re-verification on every install via `[settings] locked_verify_provenance = true` or `MISE_LOCKED_VERIFY_PROVENANCE=1`; this is **automatically turned on by paranoid mode** (`MISE_PARANOID=1` / `[settings] paranoid = true`).
- **Strict/locked mode**: `[settings] locked = true` or `MISE_LOCKED=1` makes `mise install` FAIL if any tool lacks a pre-resolved URL for the current platform in the lockfile — i.e. zero live API calls, fully offline-reproducible from the lockfile alone. Doc explicitly recommends this "for CI environments where you want to guarantee reproducible builds without any external API dependencies." NOTE the doc's own warning: `locked` is a GLOBAL setting — if set in a project's mise.toml it also applies to tools from `~/.config/mise/config.toml` (global tools), which could break unexpectedly if a global lockfile isn't also generated (`mise lock -g`).
- **Environment-specific / monorepo lockfiles**: `mise.toml` → `mise.lock`, `mise.test.toml` → `mise.test.lock`, etc. `mise.local.toml` → `mise.local.lock` (gitignored). CI without `MISE_ENV` set only touches `mise.lock`. Monorepo root-lockfile consolidation (`[monorepo] lockfile = true`) is a newer feature; doc notes "Monorepos using mise*.lock files start warning in mise 2026.12.0, and unset defaults to root lockfiles in mise 2027.6.0" — i.e. as of today (2026-07-16) this is a forward-looking migration path, not yet the default. Not directly relevant to us (we're not a monorepo per the task description) but worth knowing mise's lockfile behavior is still actively evolving.
- **`minimum_release_age` setting** (separate supply-chain feature, verbatim): defaults to `24h` — mise "limit[s] supply chain risk by only installing versions that have been available for a minimum amount of time" (protects against just-published/compromised releases). Configurable, e.g. `minimum_release_age = "7d"`. Only `npm:` and `pipx:` backends currently forward this cutoff to transitive dependency resolution; other backends apply it only to top-level tool version selection.
- CI example given directly in the doc: run `mise install` (uses `mise.lock`), and cache keyed on `hashFiles('mise.lock')`.
- **Answer to "does mise give the same tool versions locally and in CI from one file?"**: YES, verified — that is the documented purpose and mechanism (`mise.toml` for ranges + `mise.lock` for exact pins, `mise install` in both places resolves to the same locked versions), PROVIDED you actually generate and commit the lockfile (it is opt-in, not automatic) and use `mise install` (not implicit resolution) in both places. Without a lockfile, mise still gives consistent-ish results from `mise.toml` alone as long as version strings are exact (not `latest`/fuzzy), but exact reproducibility (down to checksum-verified binaries) is a lockfile feature specifically.

### mise trust / paranoid mode — VERIFIED FROM SOURCE (docs/paranoid.md and docs/cli/trust.md, jdx/mise, fetched 2026-07-16)
- Trust model exists because `mise.toml` "can contain behavior that executes code or affects the environment" (e.g., task definitions, templates). Verbatim: "Without trust, mise may prompt, skip the config in some discovery paths, fail with an untrusted-config error when it cannot prompt, or assume trust in detected CI unless paranoid mode is enabled."
- **Safe configs auto-load without any trust prompt**: files containing only `min_version`, `[tools]` entries with plain version strings (or arrays), and `[tasks]` with no templates/no tool options — "since nothing in them executes code at load time." This likely covers a simple tools-only `mise.toml` like what we'd write for pinning go/goreleaser/cosign/etc.
- **CI behavior, confirmed exact wording (docs/paranoid.md)**: "When mise detects that it is running in CI, configs are assumed to be trusted unless paranoid mode is enabled." So in normal (non-paranoid) mode, our GitHub Actions runs would auto-trust `mise.toml` without any `mise trust` step needed. This is a real, verified CI convenience (also matches jdx/mise-action having no dedicated "trust" input — consistent with auto-trust-in-CI behavior).
- **`MISE_TRUSTED_CONFIG_PATHS`** — CONFIRMED real (found in `settings.toml` source): env var / setting, list of paths mise auto-trusts without prompting; `["/"]` disables the trust mechanism entirely. Path-separator-aware (`:` Unix, `;` Windows).
- **Paranoid mode** (`MISE_PARANOID=1` or `[settings] paranoid = true`) — explicitly described by the maintainer as optional and NOT default-recommended even by mise's own author: "These are settings that I personally do not use on my own system because I find the behavior too restrictive for the benefits" (verbatim, docs/paranoid.md). Effects: all configs require trust (no CI auto-trust exemption), community plugins can't be installed by short-name (must give full git URL), all network fetches forced to HTTPS, and — as covered above — forces provenance re-verification on every install rather than trusting the lockfile.
- Trust is shared across git worktrees (based on the main checkout's trust state); global/system config files (`~/.config/mise/config.toml`) are implicitly trusted and exempt.
- **Security takeaway for us**: default (non-paranoid) mise in GitHub Actions CI auto-trusts our repo's `mise.toml` — convenient, zero extra step, but means a malicious PR that modifies `mise.toml` (e.g., adding a task with a template that executes code) would run in CI without a trust prompt, same general class of risk as any other CI config file (workflow YAML, Makefile, etc. — not unique to mise). Nothing about mise's trust model prevents a compromised repo file from running code in CI; it's aimed at protecting a *user's local machine* from an untrusted directory's config (e.g. `cd`-ing into someone else's repo), which is a different threat model than "malicious PR against our own CI."
